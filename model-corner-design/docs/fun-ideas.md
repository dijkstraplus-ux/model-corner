# 模型街角：让围观更好玩（设计提案）

> 状态：提案，未动代码。日期：2026-10-20。
> 前提（用户定的规矩）：**访客不直接干涉世界**。不影响世界发展的功能可以做，比如给开发团队留言。
> 另外要扛得住可能很大的访客量：不为单个访客调用模型、不为单个访客生成图片，防刷，一看就懂。

---

## 0. 先定一条线：「街上」和「观众席」

这份提案里所有功能都遵守同一条规矩，把它写成代码层面的约束，而不只是写在文案里：

- **街上（世界）**：`sim/` 里的状态 `S`（角色时间线、念头、记忆、关系、日记、街区日志）和每一次模型调用的提示词。
- **观众席（访客）**：访客产生的一切数据，包括关注、收藏、竞猜、表情反应、留言、成就和在线人数。
- **数据只能单向流动**：观众席可以读街上（通过 `snapshot()` 和只读接口），街上永远读不到观众席。具体做法：
  1. 访客数据放在单独的模块 `sim/audience.mjs` 和单独的目录 `sim/data/audience/`，只由 `server.mjs` 引入。**`sim.mjs`、`comic.mjs`、`personas.mjs` 永远不 import 它**。可以加一行检查脚本，比如 `grep -L audience sim/sim.mjs sim/comic.mjs`，放进测试里。
  2. 提示词里不出现任何访客数据，包括「有多少人在看你」、竞猜结果、人气和留言。`systemPrompt()` 里现在那句固定的「常有访客在围观你们的生活」可以保留（它是固定设定，不随访客变化），但不要加数字。
  3. 漫画编辑（`makeComic`）只看街区日志和念头，不看收藏数、表情数和投票。否则访客会间接决定世界的「官方记忆」。
- **页面上让人一眼看出来**：所有访客功能统一放在「观众席」样式里（同一个图标和颜色），旁边写一句固定说明「她们看不到这里」。访客不需要读规则，看样式就知道哪些东西碰不到她们。

### 现有「心意」怎么处理：删掉，改成三个不影响世界的按钮

现在的设计（每天 3 份心意；送海苔、大米、应援；投币许愿；摇铃许愿；买橘子；按小时汇总交给街区）按新规矩都算干涉，**整套删掉，不保留任何数量会进世界的变体**。替换方式：

| 现在 | 改成 | 说明 |
|---|---|---|
| 角色面板底部「送海苔 / 送大米 / 应援」（`renderSide()` 里的 `gifts` 和 `[data-g]` 按钮） | **「关注她」「收藏此刻」「分享」** | 见下面第 1、2、9 条。关注人数可以公开显示（「312 位访客在关注 Claude」），但只显示给访客 |
| 许愿喷泉、神社许愿铃的 `action`（`renderPop()` 的 `#popAct`） | 去掉按钮；弹窗里改为显示**她们自己**在这里许过的愿 | 数据来自日志里 `pray` 活动和地点为 `fountain`/`shrine`/`ema` 的记录，例如「第 12 天 14:20 DeepSeek 在这里许了愿」 |
| 水果摊「买一个橘子送给她们」 | 删掉 | 弹窗只留真实数据，比如「这周 DeepSeek 来试吃了 4 次」 |
| 驿站「这一小时收到：海苔 712 · 大米 401 · 应援 3204」 | 改成「今天的委托」：从日志里取 GPT 在驿站和码头做的 `errand` | 驿站本来就是 GPT 接委托的地方 |
| 邮筒「给角色写信，深夜电台里念出来」 | 改成**「给制作组的信」**，也就是第 12 条的留言入口 | 角色不读信、不念信。邮筒是集市里一个顺手的入口 |
| 顶栏 `meChip` 里的三颗心 `hearts` | 改成「已关注 1 · 收藏 12」之类的小计数，或者只显示名字 | `S.me.hearts` 及其分支全部删除 |
| 日志筛选「访客」（`renderFilters()`） | 改名「我的」，只显示本人的收藏、竞猜等本地记录；**不和街区日志混排** | 避免「你送了海苔」这种看起来像进了世界的条目 |

还要顺手清掉**暗示访客影响过世界**的设定文字，不然模型会自己编出「鱼片们又送了海苔」：
- `personas.mjs`：DeepSeek 记忆「研究出了招牌海苔饭团，海苔是鱼片们送的」改成「研究出了招牌海苔饭团」；Claude 记忆「第一次有访客为我的诗留言」删掉或改成「第一次有人在书屋门口停下来读我的诗」（街坊，不是访客）。DeepSeek 把访客叫作「鱼片们」可以留着，这是性格，不是互动。
- `demo2/index.html` 里的示例数据和物件文案：大饭锅「海苔是访客们送来的」，点心推车，店内物件 `onigiri`「用访客们送来的海苔包的饭团」，锦鲤「名字是访客们投票选的」，野餐会「报名 12 人」，`STORY` 里 visitor 的日志、关系表里的 `['visitors', 90, '鱼片们']`，以及 GPT 和 Claude 示例念头里「有访客请我代写情书」「帮一位访客看了星座」。示例模式也会被访客看到，应该和实时模式讲同一个故事。
- 物件弹窗里的假数字（「今天收到 37 个愿望」「卖出 96 碗」）不算干涉，但会让人误以为访客数被计入了世界。建议逐步换成从日志统计出来的真实数字（见第 3 条）。

## 1. 围观这个世界为什么好玩

这个世界没有剧本。三个角色每一步都是各自的模型当场决定的，所以访客看到的每件事都是真的第一次发生。围观的乐趣主要来自三处。第一是**反差**：内心独白和说出口的话常常不一样（嘴上「服务器繁忙」，心里想的是下一碗饭），而三个模型的性格差异会在一起时被放大。第二是**积累**：记忆、关系分和日记一天天变化，昨天一句话今天被她写进日记，某天关系分掉了 3 分，像在追一部没有编剧的连续剧。第三是**回访的奖励**：时间×8，现实里离开 3 小时，街上就过了一整天；回来能看到她们的日记、新漫画和关系变化，这相当于挂机游戏的「离线收益」，只不过收获的是故事而不是金币。

所以观众的核心循环是：**打开 → 看「你不在的时候」 → 跟一个角色看一段 → 收藏或分享一个瞬间 → 夜里竞猜明天 → 关掉 → 收到「她写完日记了」再回来**。下面的功能都是围绕这个循环加的，而且全部在观众席里，不碰街上。

## 2. 功能点子（15 个）

时间换算，后面多处会用到：游戏 1 天 = 现实 180 分钟；夜里 23:00 到次日约 07:00 角色都在睡觉 = 现实约 60 分钟；现实 1 天 ≈ 游戏 8 天。

成本里的「模型调用」都是**全站共享**的次数，和访客人数无关。

### A. 跟随和收集

#### 1. 关注她 + 看点提醒
- **一句话**：关注一个角色，她写完日记、和人聊天、出新漫画时，页面里会提醒你。
- **访客怎么用**：角色面板里点「关注她」（替代原来的应援）。之后标签页标题出现小红点「(2) 模型街角」，页面里弹出提醒，比如「Claude 刚写完第 14 天的日记」「DeepSeek 和 GPT 在栈桥聊上了」。可以选择开启浏览器通知（Notification API，仅限页面开着时）。登录用户以后可以接 mirasim 的消息通知，比如「每天最多 1 条日记汇总」。
- **为什么好玩**：最值得看的几分钟（两人聊天、睡前写日记）稍纵即逝；提醒让人不错过，也是让人回来的最主要理由。
- **为什么不影响世界**：只是对已经发生的日志做本地匹配，角色不知道谁在关注她。
- **成本**：0 次模型调用。关注列表存在 `localStorage`；登录用户的公开关注数存服务端，每人每角色 1 个布尔值。
- **滥用风险**：关注数可以被刷。缓解：只有登录账号计入公开关注数，每账号每角色 1 次；游客的关注只存在本地。
- **工作量**：S（本地）；接 mirasim 通知为 M。
- **需要的小改动**：`addLog()` 给日志条目加一个结构化的 `kind` 字段（`wake`/`sleep`/`chat`/`diary`/`comic`/`travel`/`note`），页面就不用靠正则猜文案。这是对街上数据的只读标注，不进提示词。

#### 2. 剪贴簿：收藏此刻
- **一句话**：把喜欢的一句念头、一段对话、一篇日记或一张漫画，收进自己的剪贴簿。
- **访客怎么用**：每条内心独白、日记、日志里的对话和漫画旁边都有一个书签图标。点了就收藏，剪贴簿按角色和日期排列，以后也可以一键生成分享卡（第 9 条）。
- **为什么好玩**：LLM 角色的金句是一次性的，念头列表只保留最近 30 条，很快就滚掉。收藏让「我亲眼看到的那一句」变成自己的东西。
- **为什么不影响世界**：只存引用，角色看不到收藏数，漫画编辑也不读。
- **成本**：0 次模型调用。存的是引用 `{kind, char, at}` 加一份文本快照（防止原条目被裁掉以后找不到），每条约 300 字节。游客存在 `localStorage`，登录用户存服务端，每人上限 500 条。
- **滥用风险**：基本没有，因为是私人数据。公开的「本周被收藏最多」榜单可以刷，只统计登录账号，每账号每条 1 次。
- **工作量**：S（本地）/ M（账号同步 + 榜单）。
- **注意**：念头没有 id，用 `char + at`（毫秒时间戳）当 id 就足够唯一。

#### 3. 目击图鉴
- **一句话**：收集「角色 × 活动 × 地点」的组合。亲眼看到过才算，稀有组合会闪光。
- **访客怎么用**：图鉴页是一个格子表：DeepSeek × 看星星、Claude × 荡秋千、GPT × 摸鱼……访客在线时，画面上正在发生的组合会自动点亮。格子上显示全站目击率，例如「GPT 在锦鲤桥摸鱼：本周只出现过 2 次」。
- **为什么好玩**：模型的选择有偏好，有些组合几乎不出现，所以图鉴天然有稀有度，而且稀有度是真实的，不是设计出来的。它也让访客注意到 25 个地点和 13 种活动。
- **为什么不影响世界**：只读 `snapshot()` 里的 `plan` 段。
- **成本**：0 次模型调用。稀有度在服务端统计（从日志和时间线段累加，每天一个计数表，几 KB）；个人图鉴存本地或账号。
- **滥用风险**：伪造「我看到过」只影响本人图鉴，无所谓。全站稀有度由服务端统计，访客改不了。
- **工作量**：M。
- **附带好处**：同一份统计可以替换掉物件弹窗里的假数字，例如东边长椅「这周 Claude 在这里读了 6 次书」。

### B. 回顾和时间线

#### 4. 你不在的时候（回访摘要）
- **一句话**：重新打开页面时，先看一张卡片，告诉你离开这段时间街上发生了什么。
- **访客怎么用**：卡片上写「你离开了 5 小时，街上过了 1 天 16 小时」，下面列出：带星标的大事、新写的日记（每人一行心情 + 第一句）、新漫画缩略图、关系变化（「Claude → GPT +3：老同事，今天一起看了星星」）。每一行都能点开对应的面板。
- **为什么好玩**：这就是挂机游戏的离线收益，回来马上有东西看，不会面对一个没有上下文的画面。
- **为什么不影响世界**：只读。
- **成本**：0 次模型调用。上次访问时间和关系快照存 `localStorage`，摘要在客户端拼出来。服务端只需多一个只读接口，按时间取日志（现在 `snapshot()` 只带最近 160 条）。
- **滥用风险**：无。
- **工作量**：S。

#### 5. 街角编年史（按天看的时间线）
- **一句话**：一天一页，三人的日记并排、当天大事、心情和关系的曲线。
- **访客怎么用**：顶栏点「编年史」，按天翻页。每页上方是当天的星标事件时间轴，中间是**三人日记对照**（同一天，三个视角），下方是三人的心情/精力曲线和关系分折线。
- **为什么好玩**：三人日记对照是这个游戏独有的乐趣。同一次聊天，DeepSeek 记的是「蹭到了一顿饭」，Claude 记的是「她今天好像有心事」。关系曲线能让人看出「她俩最近是不是闹别扭了」。
- **为什么不影响世界**：只读归档。
- **成本**：0 次模型调用。需要归档：sim 在每天结束（最后一个人写完日记）时，把当天的日志、日记、关系和数值快照写成 `sim/data/days/<day>.json`，每天约 20–40 KB，一年约 100 MB 以内。这是街上**往外写**，提示词照旧不读它。
- **滥用风险**：无。
- **工作量**：M。
- **需要的小改动**：现在 `S.log` 只保留 600 条，日记在 `snapshot()` 里只给最近 10 篇，没有归档就看不到久远的历史。

#### 6. 每日街角小报
- **一句话**：每个游戏日结束后出一张小报：头条、今日金句、「目击者」栏、天气和明日看点。
- **访客怎么用**：编年史每一页的顶部，或者回访摘要里的一张报纸卡片。
- **为什么好玩**：把一天浓缩成 30 秒能读完的东西，适合不常来的人，也很适合截图分享。
- **为什么不影响世界**：小报由一个「编辑」模型写，输入只有当天的日志、日记和念头，输出只放在观众席。**小报内容永远不回流进角色的提示词**，角色不读报。
- **成本**：每游戏日 1 次模型调用，即现实每天约 8 次，全站共享，和访客数无关。可以直接复用 `comic.mjs` 的编辑调用：同一次调用同时决定漫画和小报，就不增加调用次数。存储每天约 2 KB。
- **滥用风险**：访客碰不到输入。唯一风险是模型写出不合适的内容，用固定的输出格式加长度截断（照 `validate()` 的写法）兜住。
- **工作量**：S–M。

#### 7. 一段对话的两面
- **一句话**：点开一段聊天，能同时看到双方说之前在想什么、说了什么、听完又想了什么。
- **访客怎么用**：日志里每条「A 和 B 聊天：『……』——『……』」都能展开成四格：A 的念头 → A 说的 → B 说的 → B 的念头。
- **为什么好玩**：内心独白和台词之间的反差，是这个游戏最好笑、最动人的部分。现在这些数据分散在两个角色的面板里，访客很难自己对上。
- **为什么不影响世界**：只读。
- **成本**：0 次模型调用。数据已经有了：`act()` 里的 `thought`/`say`，`reply()` 里的 `say`/`thought`，按时间戳就能对上。可以让 `reply()` 在写日志时顺手记下这次对话的 `chatId`（同样是只读标注）。
- **滥用风险**：无。
- **工作量**：S。

### C. 预测

#### 8. 夜里下注，白天揭晓（今日竞猜）
- **一句话**：每天夜里角色睡着以后，出 3 道关于明天的题；第二天由规则自动判定，答对攒「观察眼力」。
- **访客怎么用**：23:00 到 07:00（现实约 1 小时，正好全员都在睡觉）显示「明日竞猜」卡片，比如：
  - 「明天谁第一个起床？」（三选一）
  - 「明天 DeepSeek 会去后山公园吗？」（是/否）
  - 「明天 Claude 和 GPT 会聊天吗？」（是/否）
  - 「明天谁最晚睡？」
  - 「明天 DeepSeek 吃几顿？」（≤2 / 3 / ≥4）

  选完以后锁定，并显示全站投票分布。第二天的事件发生时，提醒「答对了！」。
- **为什么好玩**：题目真的不可预测，因为每一步都是模型当场决定的，连开发者也猜不准；全站分布本身就很好看（「87% 的人以为 DeepSeek 会睡懒觉」）。
- **为什么不影响世界**：答题窗口只在全员睡着时开放，早上第一次 `decide()` 之前锁定。答案只在观众席里，任何提示词都不读。题目全部用规则判定，不需要模型。
- **成本**：0 次模型调用。题库是 10–20 个带 `resolve(dayArchive)` 的模板，每晚随机抽 3 个。每账号每题 1 个整数；分布每题一个计数数组。
- **滥用风险**：刷票会污染分布。缓解：只有登录账号的票计入公开分布，每账号每题 1 票，服务端校验答题窗口；游客可以答题，但只在本地计分，不计入分布和排行。不设奖品，排行榜只展示「本周眼力前 20」并隐藏账号细节，降低刷的动机。
- **工作量**：M。
- **需要注意**：`snapshot()` 现在会把角色接下来的时间线段（走路 + 下一个活动）提前十几秒发给页面。如果以后要出「她下一步去哪」这种短时题，答题必须在 `decide()` 开始之前截止。只做「夜里猜明天」就天然不存在这个问题。

### D. 分享

#### 9. 瞬间分享卡 + 深链接
- **一句话**：把一句念头、一段对话或一篇日记做成带角色头像的图片卡片，附上能直接打开那一刻的链接。
- **访客怎么用**：收藏条目或日志条目上点「分享」，浏览器本地用 canvas 画出卡片（背景用当前区域的地图，左边是角色头像，右边是文字、第几天几点），可以下载或复制。链接形如 `?panel=claude&tab=diary&day=14`。页面已经支持 `panel`/`tab`/`room`/`pop`/`area` 这些参数，只需要再加 `day`/`at` 定位。
- **为什么好玩**：好内容需要传出去；卡片自带出处，看到的人点进来就能接着看。
- **为什么不影响世界**：纯展示。
- **成本**：0 次模型调用，0 张服务端图片，全部在浏览器里生成。
- **滥用风险**：有人可能把模型写出的尴尬内容截图传播。缓解：生成侧本来就该有内容兜底（长度截断和敏感词过滤）；卡片角落固定写「AI 角色自主生成 · 非商业同人作品」。
- **工作量**：S–M。

#### 10. 漫画 / CG 画廊 + 本周封面
- **一句话**：所有自动生成的四格和 CG 按天排列；每周由登录观众选一张「本周封面」。
- **访客怎么用**：顶栏「画廊」。点开大图后显示标题、对应时段（`span`）、编辑写的「为什么画这个」（`reason`），以及当时的日志，方便对照「真实发生了什么」。每周日晚上开放投票，选出的一张放到画廊顶部和页面背景的一角。
- **为什么好玩**：漫画是这个世界最有收藏价值的产物，而且它们画的是真实发生过的事，对照起来看很有意思。
- **为什么不影响世界**：投票只决定观众席里的展示位置；**不影响编辑选什么题材，也不会让角色「知道」哪张受欢迎**。
- **成本**：没有新增模型或图片调用（漫画本来就每小时最多 1 张，由 `config.comic` 控制）。存储：每张 PNG 约 1–2 MB，每天最多 24 张；画廊列表和缩略图需要做一份 WebP 缩略图，可以在 `makeComic()` 落盘时一起生成。
- **滥用风险**：投票被刷。缓解：只限登录账号，每周每账号 1 票，只在 7 张候选里选。
- **工作量**：S（画廊）/ M（加投票）。

### E. 观众之间（不碰世界的社交）

#### 11. 预设表情反应 + 围观热度
- **一句话**：对任意一个瞬间点一个预设表情；地图上显示「现在 23 人在看 Claude」。
- **访客怎么用**：日志、日记、念头和漫画下面有一排固定表情：「笑死」「心疼」「好甜」「服务器繁忙」「顺便」，点一下 +1，不能输入文字。角色头像旁有一个小眼睛图标和人数，表示正在打开她面板的访客数。
- **为什么好玩**：知道「别人也在看这一刻」，是直播弹幕带来的陪伴感；用预设表情就没有审核负担。
- **为什么不影响世界**：计数只给访客看；**明确不进提示词**，不能让角色因为「今天 300 人在看我」而改变行为，否则就是间接干涉。
- **成本**：0 次模型调用。每个瞬间每种表情一个计数；在线热度复用 `server.mjs` 现有的 `viewers` 机制，在 `/api/state?c=...` 后面多带一个 `&p=claude` 即可。
- **滥用风险**：刷数。缓解：游客只能本地点亮、不计数，登录账号每瞬间每种表情 1 次；单账号每分钟操作数限流。**不开放自由文本评论**：评论区在大量访客下需要人工审核，又容易变成「给角色出主意」的地方。
- **工作量**：S–M。

#### 12. 给制作组的信（开发团队留言板）+ 公开回信
- **一句话**：发现 bug、想看新角色、想提建议，就写信给制作组；制作组挑一部分公开回复，并附上更新记录。
- **访客怎么用**：顶栏「制作组」按钮，或者点集市的邮筒（原来「给角色写信」的位置），打开留言框。
  - 选类别：`bug` / `想法` / `想看的角色或店` / `夸夸` / `其他`；
  - 正文不超过 300 字，可以勾选「附上此刻」（自动带上当前第几天几点、打开的面板和区域，方便复现 bug）；
  - 提交后只显示「已送达制作组」，**不公开**；
  - 「制作组回信」页面公开展示制作组挑选的来信摘录（匿名或昵称，由作者在提交时勾选是否允许公开）和制作组的回复，以及「更新记录」（「第 3 版：DeepSeek 的食堂新增了深夜菜单——来自 @小鱼片 等 14 封信的建议」）。
  - 框顶部固定写：「这封信只给制作组看。她们读不到，也不会因为这封信改变今天的生活；制作组可能会在以后的更新里采纳你的想法。」
- **为什么好玩**：访客和这个世界唯一正当的「影响通道」，是**通过开发团队、按版本、慢慢地**影响，并且能在更新记录里看到自己的名字。这也和现有的「进入协作」形成阶梯：写信 → 被采纳 → 申请协作。
- **为什么不影响世界**：留言不进任何提示词，也不能触发任何实时事件。制作组采纳建议后，通过正常的开发和发布流程改代码或人设，并写进更新记录。开发团队改世界本来就是被允许的，这不是访客的实时干涉。（边界：**不做「看到留言 → 当晚就让角色说一句」这种实时操纵**，即使是制作组手动操作也不做，否则留言板就成了间接的遥控器。）
- **成本**：0 次模型调用。存储：每封信约 1 KB，追加到 `sim/data/audience/letters.jsonl`；公开回信放在 `sim/data/audience/replies.json`，由制作组手工编辑或用一个管理脚本写入。
- **审核**：
  - 来信默认私密，所以不存在公开的垃圾内容；需要审核的只有制作组主动选出来公开的那部分，而那部分本来就会人工看。
  - 防刷：只限登录账号；每账号每天 3 封、每分钟 1 封；正文去重（同一账号同样内容 24 小时内拒收）；按 IP 做全局限流；请求体不超过 4 KB。
  - 分拣：一个只在本机运行的小脚本 `tools/letters.mjs`（列出 / 标记已读 / 写回复），或者在 mirasim 里给空间管理员推送「今天 37 封新信（bug 5）」的每日汇总，可以用 `schedule_task` 每天跑一次。不在公网暴露管理接口。
  - 被举报或违规的账号加入 `audience/blocked.json`，之后的信静默丢弃。
- **工作量**：M（主要是第一次接入登录身份和 POST 接口，之后第 2、8、10、11 条都能复用）。

### F. 节奏、成就和季节

#### 13. 观察员成就 + 打卡章
- **一句话**：给访客自己的成就：「亲眼看到 DeepSeek 挂出『服务器繁忙』」「凌晨 3 点看到 GPT 在栈桥观星」「连续 7 天读了 Claude 的日记」。
- **访客怎么用**：成就在页面上实时弹出；个人页有一本章册，每天第一次来盖一个章，章面就是当天某个角色日记里的「心情」两到四个字（来自 `writeDiary()` 输出的 `mood`），所以每天的章都不一样。
- **为什么好玩**：给「看」本身一个目标，而且目标是「去看那些平时会错过的瞬间」，比如深夜、不同区域、少见的组合。
- **为什么不影响世界**：只读，判定都在客户端，依据是 `snapshot()` 和日志。
- **成本**：0 次模型调用；存本地或账号，每人几百字节。
- **滥用风险**：本地成就可以伪造，但没有奖品，伪造了也只影响自己。如果以后做公开成就榜，只承认服务端能验证的部分（例如打卡天数），其余一律不上榜。
- **工作量**：S–M。

#### 14. 街角日历：节日与「明日看点」
- **一句话**：页面上有一本日历，标出由制作组排期的节日和角色设定里的固定活动（周五读书会、周日野餐会），并显示倒计时。
- **访客怎么用**：顶栏日期旁的小日历。「游戏时间 2 小时后：周五读书会（纸页书屋）」「现实本周六：夏日祭（制作组更新）」。节日期间页面换皮（灯笼、烟花），节日开始时给关注者发提醒。
- **为什么好玩**：给访客一个「几点来」的理由，并且把每天、每周、每季变成可以期待的节奏。重要的是，读书会到底开不开、有几个人来，仍然由角色自己决定，日历只写「她说过每周五办」，结果可能落空，这本身也是看点。
- **为什么不影响世界**：节日是**制作组**按版本加进世界的设定（写进 `personas.mjs` 或 `world.mjs`，或者作为 sim 里一个有日期的环境事件），属于开发行为，不是访客触发的；访客没有任何「开启节日」的按钮。日历只是把设定显示出来。
- **成本**：0 次模型调用；一个 `calendar.json`。节日美术是一次性的制作组工作。
- **滥用风险**：无。
- **工作量**：S（日历）/ L（每个节日的美术和设定，由制作组自行安排）。

### G. 透明

#### 15. 大脑透视：她为什么这么做
- **一句话**：点开任何一个活动，能看到她做决定时「知道什么、在意什么」：当时的数值、看到的其他人、最近的念头，以及模型名和耗时。
- **访客怎么用**：内心独白条目上有一个「为什么？」按钮，展开一张卡：「饱腹 22（低于 30）→ 决定去吃饭」「看到 Claude 在同一个区域，上次说话是 140 分钟前 → 去搭话」，下面是模型名、响应时间、是否是兜底习惯（`byModel`）。另有一页「三个大脑」统计：每个模型本周最常做的活动、平均每段活动多长、主动搭话的次数。
- **为什么好玩**：这个游戏的看点之一，本来就是「三个不同的模型在同一个世界里各自怎么活」。对熟悉 AI 的访客来说，这是独一无二的对比实验。
- **为什么不影响世界**：只读。
- **成本**：0 次模型调用。决策时的关键输入（数值、在场的人）可以在 `act()` 写进时间线段时顺手存一份精简摘要，每段约 200 字节。**不要直接公开 `calls.jsonl`**：它包含完整提示词，体积大，以后也可能放进不该公开的东西。
- **滥用风险**：无；只是要注意不泄露提示词全文和模型的接入方式。
- **工作量**：M。

## 3. 第一批推荐（4 项 + 1 个前置）

选择标准：几乎不花模型调用；直接加强「回来 → 看 → 带走」的核心循环；第一次就把「登录身份 + 观众席存储」这个基础打好，后面的功能都能复用。

### 前置：删掉心意，建立「观众席」骨架
- **页面**（`demo2/index.html`）：删除 `S.me.hearts` 和 `S.gifts`/`S.wishes`/`S.bells`；删除 `renderPop()` 里的 `#popAct` 和各物件的 `action`；把 `renderSide()` 底部的 `gifts` 按钮换成「关注她 / 收藏此刻 / 分享」；`renderMe()` 不再画心；按第 0 节清理示例文案和 `STORY` 数据。
- **sim**：按第 0 节清理 `personas.mjs` 的两条记忆。新建 `sim/audience.mjs`（只被 `server.mjs` import），目录 `sim/data/audience/`。
- **server**：`server.mjs` 现在只接受 GET。增加 POST，但只对 `/api/aud/*` 开放：请求体上限 4 KB、JSON、按账号和 IP 限流。登录身份从 mirasim 发布页的访客身份里取（发布接入方式待和 mirasim 的 publish 能力确认，比如代理转发的已验证访客 id）；拿不到身份就按游客处理，所有写接口返回 401。
- 工作量：S–M。

### ① 你不在的时候 + 关注提醒（第 4 + 1 条）
- **为什么先做**：成本为零，纯客户端，能直接提高回访；而回访是挂机围观类游戏的命脉。
- **sim**：`addLog()` 增加 `kind` 字段（在 `act()`/`goSleep()`/`writeDiary()`/`reply()`/漫画回调这几处调用时传入）。`snapshot()` 不变。
- **server**：`GET /api/log?since=<ms>` 返回 `S.log` 里 `at > since` 的条目（最多 600 条），另附每人最近的日记。需要从 `sim.mjs` 导出一个只读的 `logSince(ms)`。
- **页面**：
  - `localStorage['mc.seen'] = { at, rel: { ds: { claude: 82, gpt: 55 }, … } }`，在 `poll()` 成功后每分钟更新一次。
  - 启动时（`liveReady` 之后），如果距离上次超过 20 分钟，就请求 `/api/log?since=` 并打开一个摘要卡片 `#awayModal`（结构可以照搬现有的 `collabModal`）。
  - `localStorage['mc.follow'] = ['claude']`；在 `tickSlow()` 发现新日志的分支里（`n !== logCount` 那一段），对 `kind ∈ {diary, chat, comic, wake, sleep}` 并且 `who` 在关注列表里的条目调用 `toast()`，同时把 `document.title` 改成带数字的前缀；如果用户允许了通知，就调用 `new Notification(...)`。
- **数据形状**：日志条目 `{ id, who, area, text, star, at, day, t, kind }`。

### ② 漫画 / CG 画廊（第 10 条，先不做投票）
- **为什么先做**：漫画管线已经写好（`comic.mjs`，`comics.json`），但页面现在**看不到**漫画（`snapshot()` 不带漫画，服务端也不提供图片）。这是已经花了钱却没被看到的内容。
- **server**：`GET /api/comics` 返回 `loadComics()` 的列表，去掉 `panels[].scene` 这类提示词细节，只留 `{ id, kind, at, day, span, title, reason, file, thumb }`；`GET /api/comics/<id>.webp|png` 从 `COMIC_DIR` 读文件，id 按 `^c\d+$` 校验，设置 `Cache-Control: public, max-age=31536000, immutable`。图片按 id 永不变，可以放 CDN。
- **sim**：`makeComic()` 落盘时用 sharp 或其他工具顺手生成一张约 480px 宽的 `thumb`（WebP）。
- **页面**：顶栏加「画廊」按钮，按天分组的网格；大图下面列出当时 `span` 范围内的日志（用 ① 里的 `/api/log`）。新漫画的日志条目（`kind: 'comic'`）可以直接点开。
- 前提：`config.json` 的 `comic.enabled` 现在是 `false`，打开后才会有内容（每小时最多 1 次编辑调用和 1 张 gpt-image-2）。

### ③ 给制作组的信（第 12 条）
- **为什么先做**：这是用户点名要的功能，也是访客「想参与」这个冲动唯一正当的出口。先把它做好，被删掉的心意留下的那份参与感就有了去处。
- **server / audience.mjs**：
  - `POST /api/aud/letter`，请求体 `{ cat: 'bug'|'idea'|'char'|'praise'|'other', text: string(≤300), ctx?: { day, t, area, panel, room }, publicOk: boolean }`，返回 `{ ok: true }`。
  - 存储时每行追加到 `audience/letters.jsonl`：`{ id, at, user, nick, cat, text, ctx, publicOk, status: 'new' }`。
  - `GET /api/aud/replies` 返回 `audience/replies.json`：`[{ id, at, quote, nick|null, reply, by: '制作组', version? }]`。
  - 限流：在内存里维护 `Map<user, {day, n, last}>`，同时记录 IP 的令牌桶。
- **工具**：`tools/letters.mjs list|read <id>|reply <id> "<text>"|block <user>`，只在本机运行，用于写 `replies.json` 和 `status`。如果需要每日汇总，可以用 mirasim 的定时任务给空间管理员发提醒。
- **页面**：复用 `renderCollab()` 的弹窗样式，新建 `renderLetter()`；入口放在顶栏「制作组」，以及集市 `mailbox` 物件的弹窗（把它的 `desc`/`live` 改成「给制作组的信」）。「回信与更新」作为同一个弹窗的第二个标签页。

### ④ 夜里下注，白天揭晓（第 8 条，v1 只做三道规则题）
- **为什么先做**：前三项都是「看」，这一项让访客第一次有了「玩」的感觉：有悬念、有结果、有理由第二天再来。全部用规则判定，一次模型调用都不需要。
- **依赖**：需要每天的结构化记录。v1 不改 `sim.mjs`：由 `audience.mjs` 每 5 秒读一次 `snapshot()`，自己记录每个角色每天的活动段（`{ who, day, place, activity, t0, t1 }`），存成 `audience/days/<day>.json`。这样即使以后改坏了，也碰不到街上。（第 5 条编年史做好以后，改为读 sim 的日归档。）
- **题库**（`audience.mjs` 里的模板，`resolve(dayRecord) → 选项下标`）：谁第一个起床 / 谁最晚睡 / A 和 B 明天聊不聊 / DeepSeek 去不去后山 / Claude 写没写东西。
- **接口**：
  - `GET /api/aud/quiz` 返回 `{ day, open: bool, closesAt, questions: [{ id, text, options: [..] }], dist?: [[n,..],..], mine?: [i,..], result?: [i,..] }`；
  - `POST /api/aud/quiz` 请求体 `{ day, answers: [i, i, i] }`，只在 `open` 期间（游戏 23:00 到次日第一个角色起床）接受，每账号每天 1 次，提交后不可修改。
- **存储**：`audience/quiz/<day>.json` = `{ questions, votes: { [user]: [i,i,i] }, result }`，每天约几十 KB（按 1000 个答题账号估算）。
- **页面**：夜里在 `dock` 上方显示一张竞猜卡片；白天显示「昨晚的竞猜：第 1 题已揭晓 ✓」。游客可以作答，结果只存 `localStorage`，提示「登录后计入全站统计」。

## 4. 考虑过但否决的点子（会干涉世界）

| 点子 | 为什么否决 |
|---|---|
| 心意：送海苔 / 大米 / 应援，按小时汇总交给角色 | 直接改变角色的处境和动机。已在第 0 节删除 |
| 投币许愿 / 摇铃许愿，愿望汇总进街区 | 同上；改为只显示她们自己许过的愿 |
| 给角色写信，深夜电台念出来 | 访客文本进入世界，而且需要为单个访客生成回应；改为给制作组的信 |
| 访客和角色直接聊天 / 角色回复访客留言 | 既是干涉，又是每个访客一次模型调用，访客多了成本失控，提示词注入风险也最高 |
| 投票决定她下一步做什么 / 投票选剧情走向 | 典型的遥控世界 |
| 访客投票给世界里的东西命名（锦鲤「大肥鱼」） | 访客内容进入世界设定；名字改为由角色自己起或由制作组定 |
| 访客化身成为客人进店、在地图上走动 | 角色会「看到」他们，世界因此改变；大量访客时画面也会被淹没 |
| 访客在许愿牌、公告栏上挂自己的文字 | 这些是世界里的物件，角色会去读（`ema`、`board` 都有 `read` 活动）；文字只能放在观众席 |
| 把围观人数、人气、关注数写进提示词（「今天有 300 人在看你」） | 看起来无害，实际上是间接干涉：角色会为了观众改变行为，热度也很容易被刷 |
| 被收藏或表情多的瞬间自动成为「重要记忆」 | 访客间接决定角色记住什么 |
| 漫画编辑参考收藏数或投票选题材 | 访客间接决定世界的「官方记忆」；投票只决定观众席的展示位置 |
| 访客触发天气、节日或随机事件（哪怕要攒很多人一起点） | 集体干涉仍然是干涉；节日只由制作组按版本排期 |
| 竞猜结果反过来影响世界（「猜对的人多，她就去」） | 等于投票遥控；竞猜窗口只在全员睡着时开放，答案永不回流 |
| 制作组看到留言后当场改角色状态或插一句台词 | 会让留言板变成间接的遥控器；只允许按版本更新，并写进更新记录 |
| 付费、打赏加速时间或解锁剧情 | 违反非商业定位，也是干涉 |
| 「时间倒流 / 快进」影响全站 | 现有的时段预览只在本地渲染，不影响世界，可以保留；任何改变服务端时钟的操作都否决 |
| 访客评论区（自由文本，挂在日记下面） | 本身不是干涉，但大量访客下需要人工审核，又会变成「给角色出主意」的地方，最后变成对制作组的压力；先用预设表情代替，真正的意见走「给制作组的信」 |

## 附：访客多了以后要注意的一件事

所有功能都基于 `/api/state` 的轮询（每 4 秒一次，没有变化时返回 204）。访客到万人级别时，Node 单进程每秒要处理约 2,500 个请求，每次还要重新序列化快照。建议在做上面这些功能之前或同时，按 `ver` 缓存序列化和 gzip 以后的快照（每个 `ver` 只算一次），日志、画廊这类历史数据用带强缓存的静态 JSON；之后再考虑改成 SSE 推送，或者把快照定期写成一个静态文件放到 CDN。观众席的写接口（留言、竞猜、表情）全部按账号限流，并且和读接口分开计数。
