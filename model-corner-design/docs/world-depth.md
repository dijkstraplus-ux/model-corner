# 模型街角：世界的深度与可扩展的游戏框架（设计提案）

> 状态：P1、P2、P3 都已实现并在线（2026-10-20）。下面是当初的提案，实现时的差异：钓鱼挪到了集市的小码头尽头（后山钓鱼台四面是水，走不过去）；
> 灯塔在礁石上，大家在海堤上看它，只有 GPT 能飞上去修灯；周日白天野餐会、晚上灯笼节，周六晚上流星雨；动作对应的动画行写在 `sim/content/poses.json`，
> 新的动作图集是每人三张 `<id>-act8b/c/d`（搅锅、捏饭团、端盘子、坐下、荡秋千、蹲着堆沙、盖被子睡、写字、祈愿、钓鱼……），道具图 `props.webp`。
> 对象：`model-corner-design/sim/`（街上）和 `demo2/index.html`（页面）。观众席的部分见 `docs/fun-ideas.md`，本文只讨论**街上**。
> 不变的前提：访客不影响世界；每个角色由自己同名的模型驱动；活动按正常的现实节奏进行（一件事持续几分钟，不是几秒）；模型调用要便宜（现在约每现实小时 20 次决策，提示词约 2k tokens）。

---

## 0. 一页摘要

**问题。** 现在的世界只有「地点 + 13 种活动」。地点没有状态，活动做完不留下任何东西，所以模型只能围着仅有的一点内容（《雨天的书签》、小黑板、饭团）和彼此打转。第 1 天的真实记录里，三人 45 次决策只去过 25 个地点中的 7 个。DeepSeek 和 Claude 一整天没离开广场。Claude 23 次输出里提到「黑板」25 次。日志里「X 去了 Y」比真正发生的事还多。3 张漫画中有 2 张重复画了同一段剧情。

**方案。** 把「地点 + 活动」升级成「**物件 + 动作 + 会持久保存的世界状态**」：
- 模型只负责**选**（从一张按相关度排好的「现在能做的」短清单里选，也可以自由写），世界的变化由系统按数据规则**结算**。
- 在此之上加几层，全部由数据描述：物品与借还、请求与人情、多人聚会（有分工）、跨天推进的项目、日程/节日/天气/意外，以及比一个分数更丰富的关系（共同经历、梗、人情、约定）。
- 所有内容放在 `sim/content/*.json`。加新内容就是加数据，只有新增一种「效果操作」时才需要改代码。
- 每一次有意义的变化都记进**事件簿（episode）**。日记、页面和漫画编辑都从事件簿取材。

**分三期。**
| 期 | 名字 | 工作量 | 模型调用 | 提示词 | 新美术 |
|---|---|---|---|---|---|
| P1 | 世界会记住东西 | 2–3 人日 | 不变 | 基本持平（+0～15%） | 无 |
| P2 | 她们之间 | 4–6 人日 | 约 +3～5 次/现实小时 | 只在有人在身边时 +100～200 tokens | 可选：1 张道具图 |
| P3 | 会长大的街区 | 1.5–2 周 | +0～2 次/现实小时 | 持平 | 每人 1 张新动作图，加 1–2 张节日装饰，共约 5 张 |

**为什么漫画会受益最大。** 漫画和 CG 是 gpt-image-2 每次现画的，不受精灵图只有 4 行动作的限制。只要世界能产生具体的事实（沙堡被潮水冲掉一半、读书会只来了一个人、账本里 30% 的钱花在了「试吃」上），漫画就能画出来。所以投入世界深度，最先在漫画上见效，而且不需要等新的精灵图。

## 1. 诊断：现在的世界为什么浅、为什么重复

数据来源：`sim/data/calls.jsonl`（71 条：45 次成功决策、7 次 codex 失败、9 次回应、2 篇日记、4+4 次漫画）和 `sim/data/state.json`（第 1 天 07:00–20:49）。

### 1.1 世界没有状态，模型只能反复回到唯一「有内容」的东西上
- 小黑板是全街唯一能留下文字的东西（Claude 写了推荐，GPT 又添了一段）。它吸走了 **10/45 次决策**。Claude 的 23 次输出（决策加回应）里「黑板」出现 **25 次**，念头里「把黑板上的字再理一理」类的话出现 **4 次**。因为黑板上写了什么并没有被保存，她每次只能重新「理一理」。
- 道谢也形成了死循环：Claude 的念头里「好好谢她一句」出现 3 次，台词又谢了 2 次，谢的都是同一段推荐语。原因是聊天之后世界里没有留下「已经谢过」这个事实。
- 口头禅被放大成填充词：GPT 11 次输出里「顺便」出现 14 次，DeepSeek 20 次输出里「饭团」出现 25 次。人设是唯一的素材来源，于是每句话都在复读人设。

### 1.2 「干活」是空壳
DeepSeek 17 次决策里有 10 次在食堂，其中 6 次是 `work`，`doing` 基本是「回店里摆饭团看摊」的变体，原句至少出现 3 次。食堂没有库存、没有客人、没有锅的状态，所以「看店」和「看店」之间没有任何区别，模型也就没有理由做别的选择。GPT 的「接委托」同样只是一句话，委托板上没有一张真正的委托。

### 1.3 地图很大，生活半径很小
- 25 个地点里，模型只选过 7 个：diner 17、blackboard 10、bookstore 8、benchE 5、observatory 2、benchW 2、jetty 1。
- DeepSeek 和 Claude 一整天没离开广场。GPT 只有早上一次去码头是模型选的；13:17 以后 codex 通道报 `pgrep -x codex` 失败，之后去集市和后山的 5 趟全部来自兜底习惯，轮流是驿站、码头、秋千、万事屋，世界没有因此发生任何变化。
- 系统提示里的 25 行地点清单有 937 字，占系统提示（2,177 字）的 43%。它告诉模型「能去哪」，却没有说「为什么要去」：那里现在是什么样、有什么在等她。

### 1.4 世界里只有彼此，所以社交过多但内容空洞
- **25/45 次决策**填了 `talk_to`，Claude 是 14/19，尽管系统提示里写了「不要每件事都去找人聊」。`chat` 活动占 13/45。
- 每次聊天只有一来一回（A 说一句，B 用自己的模型回一句），然后就结束了；也没有可聊的话题，只能寒暄、道谢、夸新书。

### 1.5 Bug：`talk_to` 把告别变成了走过去
`act()` 里只要填了 `talk_to`，就会把目标改成对方身边。模型却常把它当作「这句话是对谁说的」：
- Claude（游戏 11:21）选了 `bookstore / write`，`talk_to: gpt`，说「我先回书屋了，黑板还等着我呢。」结果她留在了食堂（GPT 在那里），`today` 里记的是「深海食堂：在书屋理黑板排版」。
- Claude（游戏 17:00）选了 `bookstore / write`，`talk_to: ds`，说「我回书屋改改稿子，你慢慢晒太阳。」结果是「DeepSeek身边：在书屋里改稿子」。

画面和文字因此对不上，「离开」这个动作也不会发生。

### 1.6 Bug：关系分从来没变过
`writeDiary()` 让模型按「对方 id」输出 `relations`，但给它看的 `relLine()` 只写了名字。两篇日记返回的键都是 `"DeepSeek"`、`"GPT"`、`"Claude"`，被 `if (!c.rel[k]) continue` 全部丢掉了。第 1 天结束时，6 个关系分和初始值完全一样（82/55/78/70/76/60）。

### 1.7 人设里承诺的东西，世界里都不存在
「每周五 19:00 读书会」（sim 没有星期的概念）、「深夜半价」、「明天再堆完沙堡」（沙堡没有进度）、「服务器繁忙」的牌子、委托板、宝库的金币、DeepSeek 抱去书屋的账本，在 sim 里都没有对应的数据。页面上的物件弹窗全靠假数字撑着，比如「今天已经卖出 96 碗」「完成度：60%」「板上还有 3+n 张没人接的委托」。

### 1.8 晚上是空的
基础精力每游戏小时 −4，`work` 再 −4，`rest` 只 +5，第 1 天平均每小时约 −4.8。三人从 78–85 起步，到傍晚精力都只剩 18–25，Claude 19:30、DeepSeek 19:57 就上床了。设定里最有画面感的晚间内容（观星、周五读书会、深夜半价）全部落在她们的睡觉时间。夜里约 11 个游戏小时（现实约 80 分钟）什么都没发生。

### 1.9 日志和漫画的素材很薄
- 24 条日志里：走动（「X 去了 Y」）9 条，聊天 6 条，模型自己写的 `log` 只有 4 条，其中 2 条是同一件事（GPT 写推荐语，被 GPT 和 Claude 各记了一次）。
- 3 张漫画里，第 1、2 张都画了 11:05 GPT 来吃饭团，第 2、3 张都画了 15:30 长椅上一起晒太阳。漫画编辑不知道之前画过什么，而这段时间里也确实没有别的事可画。

### 1.10 没有模型时，世界就停住了
兜底习惯（`HABITS`）只是在 5 个固定组合里随机挑一个，做完不改变任何东西。GPT 那半天就是这样。

### 1.11 提示词里的低价值内容
- 「街上最近的事」主要是走动记录。
- 「你今天做过」把 10 条原文整段贴进去，约 530 字，占用户消息的 39%，信息却高度重复。
- 记忆不去重：Claude 第 1 天新增了 10 条记忆，其中有「下午在广场东边长椅看书，想再读一遍《雨天的书签》」这种琐事；DeepSeek 的记忆里也有「Claude 回书屋改稿去了」。DeepSeek 17 次决策一条 `remember` 都没写。

**结论：** 问题不在模型。世界没有给她们**可以改变的东西**、**需要别人的理由**和**明天还要继续的理由**。

## 2. 框架设计

### 2.0 六条原则
1. **模型负责选，系统负责结算。** 模型给出意图（选项、说的话、写下的字），世界怎么变由数据规则决定。模型编出来的状态（比如「给了她 3 个饭团」，其实手里没有）不会生效。
2. **内容就是数据。** 物件、动作、物品、聚会、日程、意外、NPC 委托都写在 JSON 里。代码只实现十来种通用的「条件」和「效果」。
3. **只给相关的。** 提示词里不列「全部」，只列和她此刻有关的几行，每一块都有行数上限。
4. **状态有上限。** 每种列表都有容量，旧的会过期或归档。
5. **变化要留痕。** 有意义的结算都写进事件簿，日记、页面和漫画都读它。
6. **与访客隔离。** 新模块不读观众席的任何数据；随机数用游戏日做种子；日程、意外和 NPC 委托都由制作组编写。

### 2.1 核心概念

| 概念 | 是什么 | 例子 |
|---|---|---|
| 物件 Thing | 地点上一个有状态的东西 | 鲸鱼电饭煲（空/在煮/煮好/凉了）、沙堡（48%）、小黑板（三行字） |
| 动作 Verb | 物件提供的一种做法，映射到 13 种现有活动之一（所以动画、数值、图标都沿用现有的） | 煮饭→`work`，堆沙堡→`play`，挂许愿牌→`pray` |
| 世界状态 `S.world` | 物件状态、背包、项目、聚会、请求、羁绊、事件簿、天气，存在 state.json 里 | |
| 物品 Item | 可以拿、给、借、吃、放的东西 | 饭团、《雨天的书签》、DeepSeek 的账本、伞 |
| 项目 Project | 跨天推进、有进度、会产出东西的事 | Claude 的新短篇（5 段）、DeepSeek 的新菜、GPT 的星图 |
| 聚会 Gathering | 多人一起做的事，有角色分工，按回合说话 | 一起吃饭、读书会、观星、一起堆沙堡 |
| 请求 Request | 一个角色请另一个帮忙；或 NPC 贴在委托板上的委托 | 「帮我理账本」「渔夫：补船帆」 |
| 日程 / 意外 / 天气 | 由时间驱动的世界变化（制作组编写，用种子随机） | 周五读书会、21:00 涨潮、猫叼走饭团、午后下雨 |
| 羁绊 Bond | 两个人之间的共同经历、梗、人情和约定 | 「书借我闻闻就行」、DeepSeek 欠 Claude 两次人情 |
| 事件簿 Episode | 一件值得记住的事的结构化记录 | 「涨潮冲掉了半个沙堡（她说过 5 次明天再堆）」 |
| NPC | 只存在于文字里的街坊，不上画面，不需要美术 | 渔夫老海、花摊婆婆、邮差小鸥、点心推车小哥 |

### 2.2 文件结构

```
sim/
  content/                 纯数据：加内容只改这里（用 import … with { type: 'json' } 引入，预计 node --watch 会跟着重载；实测不行的话，就像 nav 网格那样 touch world.mjs）
    places.json            现在 world.mjs 里的 PLACES 挪过来，并加上新地点（钓鱼台、灯塔）
    things.json            物件、状态、动作、计时器、日结
    items.json             物品
    projects.json          项目模板
    gatherings.json        聚会模板
    calendar.json          日程和节日
    incidents.json         意外
    npcs.json              NPC 名字和委托模板
    weather.json           天气的转移概率
  content.mjs              加载并校验：引用不存在的 id 时打印错误、跳过该条，保留上一份正确的内容，不会让 sim 崩掉
  rules.mjs                条件和效果的小解释器（不用 eval）
  worldstate.mjs           S.world 的初始化/迁移、开始和结算、世界时钟、日结、快照
  menu.mjs                 拼给模型看的几块文字：「现在能做的」「世界此刻」「你的事」「你们之间」
  social.mjs               请求、邀请、聚会回合、羁绊、事件簿
  sim.mjs                  原有：时钟、时间线、决策循环（改动见 2.15）
  world.mjs                保留 AREAS/LINKS/SHOPS/ACTIVITIES/ANIM/route()；PLACES 改为从 content 读入
```

### 2.3 物件和动作（things.json）

三个例子，覆盖「锅在煮」「进度会被潮水冲掉」「能写字」三种典型情况：

```json
[
  {
    "id": "pot", "name": "鲸鱼电饭煲", "place": "diner", "page": { "room": "diner", "obj": "cooker" },
    "state": { "rice": "empty", "readyAt": null },
    "show": [["rice == cooking", "锅里正在煮饭"], ["rice == ready", "饭煮好了，还冒着热气"], ["rice == cold", "饭在锅里放凉了"], ["", "锅是空的"]],
    "verbs": {
      "cook":  { "label": "煮一锅饭", "act": "work", "who": "owner", "minutes": [20, 40],
                 "need": "rice == empty || rice == cold",
                 "start": { "set": { "rice": "cooking", "readyAt": "+40m" } } },
      "shape": { "label": "捏饭团", "act": "work", "who": "owner", "minutes": [30, 60],
                 "need": "rice == ready",
                 "end": { "set": { "rice": "empty" }, "add": { "counter.stock": 8 } } }
    },
    "timers": [
      { "when": "rice == cooking", "at": "readyAt", "set": { "rice": "ready" } },
      { "when": "rice == ready", "after": "180m", "set": { "rice": "cold" }, "log": "深海食堂的饭在锅里放凉了", "episode": { "w": 1 } }
    ]
  },
  {
    "id": "sandcastle", "name": "沙滩上的沙堡", "place": "sandcastle", "page": { "area": "market", "obj": "sandcastle" },
    "state": { "pct": 35, "builders": [], "flag": "", "postponed": 3 },
    "caps": { "builders": 3 },
    "show": [["pct >= 100", "沙堡堆好了{flag}"], ["", "沙堡堆了 {pct}%（DeepSeek 已经说了 {postponed} 次「明天再堆」）"]],
    "verbs": {
      "build": { "label": "接着堆沙堡", "act": "play", "minutes": [30, 90], "slots": 3,
                 "need": "weather != rain && hour >= 6 && hour < 19 && pct < 100",
                 "end": { "add": { "pct": "12/h" }, "push": { "builders": "$who" } },
                 "milestone": [{ "when": "pct >= 100", "log": "{builders} 堆完了沙堡！", "star": true, "episode": { "w": 3 } }] }
    },
    "daily": [{ "at": "21:00", "when": "pct < 100", "mul": { "pct": 0.5 }, "log": "涨潮了，沙堡被冲掉了一半", "episode": { "w": 2 } }],
    "counters": { "postponed": { "who": "ds", "match": "明天.{0,8}沙堡|沙堡.{0,8}明天", "in": ["thought", "diary"] } }
  },
  {
    "id": "blackboard", "name": "书屋门口的小黑板", "place": "blackboard", "page": { "area": "square", "obj": "blackboard" },
    "state": { "lines": [] }, "caps": { "lines": 3 }, "text": true,
    "show": [["", "{lines}"]],
    "verbs": {
      "write": { "label": "在黑板上写一句", "act": "write", "minutes": [15, 30], "cooldown": "120m", "writes": 30,
                 "end": { "push": { "lines": { "by": "$who", "text": "$text" } }, "bump": true } },
      "read":  { "label": "看看黑板上写了什么", "act": "read", "minutes": [10, 20], "end": { "see": true } }
    }
  }
]
```

各字段：

| 字段 | 说明 |
|---|---|
| `place` | 站在哪个地点（`places.json` 的 id，站位逻辑沿用现有的 `stand`/`standAt()`） |
| `page` | 对应页面上的哪个物件（`AREAS[area].objects[].id` 或 `ROOMS[room].objects[].id`），供页面读取真实状态 |
| `state` / `caps` | 初始状态；列表的容量（超出时丢掉最旧的） |
| `show` | 按顺序匹配的条件和文字，第一条命中的就是显示内容。既给页面弹窗用，也给模型看（压成一行） |
| `text: true` | 这个物件上有文字，引入「看没看过」机制（2.5） |
| `verbs.*.act` | 映射到 13 种现有活动之一。`ANIM`、`RATE`、图标全部沿用，所以**不需要新动画** |
| `who` | `owner`（只有店主能做）、`guest`、`any`，或某个角色 id（专属动作，比如只有 GPT 能读准水晶球） |
| `minutes` / `slots` / `cooldown` | 时长范围；同时能有几个人（`standAt()` 已经会错开站位）；同一个人多久之后才能再做 |
| `need` | 条件表达式（下表） |
| `start` / `end` / `milestone` | 开始时、结束时、达到条件时执行的效果 |
| `timers` / `daily` / `passive` | 世界自己的钟：到点触发、每天某个时刻触发、每隔一段时间触发（比如没人看店时街坊自己拿饭团） |
| `counters` | 用正则统计某个角色的念头或日记，把「梗」变成可以展示的数字（「她已经说了 5 次明天再堆」） |
| `fail` | 不是专属角色时有概率失败，失败时从几句日志里挑一句，比如「DeepSeek 修秋千，把绳子打成了蝴蝶结」 |

**条件**（`need` / `when`）：用 `&&` 和 `||` 连接比较式（`== != > >= < <=`）。左边可以是本物件的字段（`pct`）、别的物件的字段（`counter.stock`）、`hour`、`weekday`（1–7，第 1 天是周一）、`day`、`weather`、`$owner`、`$has(onigiri)`、`$with`（此刻在这个物件上的人数）、`$food/$energy/$mood`。右边是数字或不带引号的词。`rules.mjs` 用一个正则加一个小循环解析，不用 `eval`。

**效果**：

| 操作 | 例子 | 说明 |
|---|---|---|
| `set` | `{"rice": "cooking", "readyAt": "+40m"}` | 设值。`+40m` 表示从现在起的游戏分钟；`$who`、`$text`、`$item` 会被替换 |
| `add` | `{"pct": "12/h", "counter.stock": 8}` | 加减。`n/h` 按这段活动的游戏小时数折算；结果不会低于 0 |
| `mul` | `{"pct": 0.5}` | 乘 |
| `push` | `{"lines": {"by": "$who", "text": "$text"}}` | 追加到列表，受 `caps` 限制 |
| `give` / `take` | `{"k": "onigiri", "n": 2, "to": "$who"}` | 物品进出某人的背包或物件的库存 |
| `stat` | `{"mood": 4}` | 一次性改数值（持续的仍按 `RATE`） |
| `progress` | `{"project": "$active", "n": 1}` | 推进项目 |
| `see` / `bump` | `true` | 标记「她看过了」/「内容更新了，其他人变成没看过」 |
| `log` | `"{builders} 堆完了沙堡！"` | 由系统按模板写街区日志，可以加 `star` |
| `episode` | `{"w": 2, "title": "…"}` | 记进事件簿，`w` 是权重 |
| `maybe` | `{"p": 0.3, "then": {…}}` | 按概率执行（用种子随机） |

### 2.4 世界状态、持久化、结算时机

`S.world` 的形状（存在 state.json 里，和 `S.chars` 并列）：

```json
{
  "v": 1, "seq": 120, "clock": 4380,
  "things": { "pot": { "rice": "ready", "readyAt": 4200, "ver": 3, "seen": { "ds": 3 } }, "sandcastle": { "pct": 48 } },
  "inv": { "ds": [{ "k": "onigiri", "n": 2 }], "claude": [{ "k": "book", "id": "i1", "title": "雨天的书签", "author": "claude" }], "gpt": [] },
  "projects": {}, "gatherings": {}, "requests": {}, "bonds": {}, "agenda": {}, "episodes": [],
  "weather": { "day": 3, "today": "cloudy", "rain": [17, 20], "tomorrow": "clear" }
}
```

一个动作从选择到结算的完整过程：
1. **决定**（`decide()`）：`menu.mjs` 生成选项，模型选一个，`validate()` 检查硬条件和槽位（槽位通过扫描所有人计划里与该时段重叠、且 `seg.thing` 相同的段来算）。
2. **排进时间线**（`act()`）：活动段上多带 `thing`、`verb`、`text`（写下的字）、`gid`（聚会 id）。
3. **开始**：在 `tick()` 里新增 `startDue(now)`，`t0` 到了就执行 `verb.start`（比如锅开始煮），并设 `seg.started = true`。
4. **结束**：在 `tick()` 里新增 `settleDue(now)`，或者在 `decide()` 提前 `LEAD` 秒结算上一段时一起做（和现在的 `applyStats()` 同一个位置）。执行 `applyStats` + `verb.end` + `milestone` + 写事件簿，并设 `seg.settled = true`。这样下一次决策时，她能看到自己刚刚造成的变化。
5. **世界自己的钟**：`tick()` 里新增 `worldClock(gameMin)`，每过一个游戏分钟最多跑一次，依次处理 `timers`、`passive`、日程、聚会开场，以及 05:00 的日结（掷当天天气、重置库存和售出数、刷新 NPC 委托、清理过期的请求和约定、归档旧事件簿）。
6. **幂等与补跑**：所有结算都靠 `started`/`settled`/`world.clock` 这几个标记，不会重复执行。服务停机后，`load()` 按时间顺序补跑计时器和日结（最多补 3 天）。

迁移：`load()` 里如果没有 `S.world` 就执行 `initWorld()`；`v` 字段用于以后的迁移。小黑板的初始内容直接用第 1 天真实发生过的事：「今日推荐：《雨天的书签》」和 GPT 添的推荐语。

### 2.5 「看见」和「知道」
文字类物件（小黑板、公告栏、许愿牌、委托板）有 `ver`，每次 `bump` 加 1；`seen[角色] = 她看过的版本`。
- 只有亲自 `read`，或者在那里做别的事，才算看过。在「世界此刻」里，没看过的会写成「小黑板（GPT 2 小时前写了一句，你还没看）」，于是她有了一个具体的理由出门。
- P2 再加「听说」：聊天时，如果台词里提到某个物件的名字，听的人会得到一句**梗概**（不是全文），比如「听说黑板上 GPT 写了推荐语」。
- 页面不受这个限制，访客能看到全部内容。「她还没看到，我已经看到了」这种信息差本身就是看点。

### 2.8 日程、节日、天气、意外

```json
[
  { "id": "reading_club", "weekly": 5, "at": "19:00", "gathering": "reading", "host": "claude", "announce": "-12h" },
  { "id": "late_half", "daily": true, "at": "22:00", "until": "23:30", "set": { "counter.halfprice": true }, "line": "深海食堂深夜半价（22:00–23:30）" },
  { "id": "picnic", "weekly": 7, "at": "11:00", "gathering": "picnic" },
  { "id": "market_day", "weekly": 3, "set": { "fishstall.special": "鲷鱼" }, "line": "集市日：鱼摊有新鲜鲷鱼" },
  { "id": "meteor", "day": 9, "at": "21:00", "line": "流星雨", "force": { "weather": "clear" }, "forecastBy": "gpt", "forecast": "-2d" },
  { "id": "lantern", "day": 14, "at": "18:00", "until": "23:00", "festival": "灯笼节", "set": { "tree.lanterns": true } }
]
```

- **星期**：第 1 天是周一，`weekday = (day - 1) % 7 + 1`。游戏里的一周等于现实约 21 小时，所以周五读书会大约现实每天一次，访客有了「几点来看」的理由。
- **天气**：05:00 日结时，用 `weather.json` 的转移概率表，以当天的天数做种子掷出今天和明天的天气（以及雨的时间段）。天气通过条件影响动作（下雨不能堆沙堡，阴天不能观星），也影响数值（雨天在室外心情 −1/h）。页面上，风向标和水晶球显示真实天气，地图上加雨、雾的粒子和色调（画布效果，不需要新美术）。
- **水晶球是 GPT 的专属动作**（`who: "gpt"`）：她能提前知道明天的天气和流星雨，可以把预报贴到公告栏，其他人读过后才知道。这样「她什么都知道」的人设有了实际作用。
- **意外**（incidents.json，P3），每天最多 2 件，按权重抽取：

```json
[
  { "id": "cat_onigiri", "when": "counter.stock > 0 && hour >= 10 && hour < 16", "w": 2,
    "do": { "add": { "counter.stock": -1 }, "set": { "cat.has": "onigiri" } }, "log": "一只猫叼走了深海食堂的一个饭团", "episode": { "w": 2 },
    "resolve": { "thing": "cat", "verb": "chase", "label": "追回被叼走的饭团" } },
  { "id": "swing_rope", "when": "swing.rope == ok", "w": 1, "do": { "set": { "swing.rope": "broken" } }, "log": "古树上的秋千绳断了一根" },
  { "id": "wind_board", "when": "weather == windy", "w": 1, "do": { "set": { "blackboard.lines": [] } }, "log": "一阵大风把小黑板上的字吹花了" }
]
```

`resolve` 会在相关的人的菜单里加一个临时选项，比如 GPT 看到「秋千断了」，她的「顺便修」人设就有了真正的对象。

### 2.9 多人活动和角色分工（gatherings.json，P2）

```json
{
  "meal":     { "name": "一起吃饭", "place": "diner", "minutes": 60, "rounds": 1,
                "roles": { "host": { "who": "owner", "act": "work", "label": "下厨招待" }, "guest": { "act": "eat", "label": "一起吃", "max": 3 } },
                "after": { "give": { "k": "onigiri", "n": 0 }, "log": "{host} 请{guests}吃了一顿饭" } },
  "reading":  { "name": "读书会", "place": "bookstore", "minutes": 90, "rounds": 2, "need": "$hostHas(book)",
                "roles": { "host": { "act": "read", "label": "主持、朗读" }, "guest": { "act": "read", "label": "听、发言", "max": 4 } },
                "empty": { "after": "20m", "log": "读书会没有人来，{host} 一个人读完了第一章", "episode": { "w": 2 } } },
  "stargaze": { "name": "一起观星", "place": "pier", "minutes": 60, "rounds": 1, "need": "weather == clear && hour >= 19",
                "roles": { "host": { "act": "stargaze", "label": "指给大家看" }, "guest": { "act": "stargaze", "label": "看星星", "max": 2 } } },
  "build":    { "name": "一起堆沙堡", "place": "sandcastle", "thingVerb": "sandcastle/build", "minutes": 60, "rounds": 1,
                "roles": { "any": { "act": "play", "max": 3 } }, "bonus": { "pct": 1.5 } }
}
```

聚会实例：

```json
{ "id": "g7", "kind": "reading", "host": "claude", "place": "bookstore", "at": 6900, "until": 6990,
  "invited": ["ds", "gpt"], "rsvp": { "ds": "yes", "gpt": "maybe" }, "present": [], "status": "planned",
  "topic": "《雨天的书签》第二章", "src": "calendar:reading_club", "lines": [] }
```

流程：
1. **发起**：来自日程（周五读书会）、决策里的 `invite`（「claude,gpt:meal@19:00」），或主持人在 `announce` 时间把告示贴到公告栏。
2. **回复**：如果是当面邀请，对方在 `reply` 里填 `answer: yes/no/maybe`；否则被邀请的人下次决策时，「你的事」里会有一行邀请，菜单里也有「去赴约」选项（快到时间时排到第一）。
3. **到场**：选了赴约的人，时间线排成先走过去，在 `at` 之前做一段「等大家」（`rest`），然后是一段从 `at` 到 `until` 的聚会段（`seg.gid`）。没来的人不会被强行拉过来：「说好要来却没来」会进入羁绊，也是素材。
4. **回合**：聚会进行到 1/3 和 2/3 时各有一个回合（`rounds` 决定有几个）。主持人用自己的模型说一句（新的 `kind: 'scene'`，提示词很小：在场的人、话题、上一回合的台词），然后每个到场的人用**自己的**模型回一句（复用 `reply()`，多传一句情境）。台词按时间错开写进各自活动段的 `says`，页面上就是轮流冒出的气泡。
5. **收尾**：执行 `after` 的效果，写一条街区日志和一条事件簿，参与的人两两之间的羁绊加上 `shared`。
6. **花费**：聚会期间所有人都在同一段长活动里，不会触发 `decide`，所以回合调用**替代**了原本会发生的决策。读书会（1 主持 + 2 客人，2 个回合）最多 6 次调用，每游戏周一次；饭局 2–3 次。净增加的很少。
7. **页面**：`ROOMS[*].spots` 现在只有两两相对的 `pair`。要加上三人座的 `group`（比如食堂的 `tableL`、`tableL2`、`counter` 三个位置，书屋的 `rugA`、`rugB`、`tea`），`roomLayout()` 遇到同一个 `gid` 的人时，先找一组空着的座位。

### 2.11 关系：不只是一个数字（P2）

```json
"bonds": {
  "claude|ds": {
    "shared": ["e12", "e31"],
    "jokes": [{ "text": "书借我闻闻就行", "by": "ds", "day": 1, "used": 1 }],
    "owe": { "ds": 2, "claude": 0 },
    "promises": [{ "id": "p3", "by": "claude", "to": "ds", "text": "明天教你记账", "due": 2880, "status": "open" }],
    "topics": { "推荐语": 1 },
    "last": 2850
  }
}
```

- **共同经历** `shared`：两人都参与的事件簿条目，最多保留 8 条，按权重和新近程度排序。
- **梗** `jokes`：来自日记新加的 `joke` 字段，以及物件上的 `counters`（「明天再堆沙堡」）。每对最多 5 条，很久没用的先淘汰。
- **人情** `owe`：完成一次请求加 1，回礼（`give`）或反过来帮一次就抵消。在「你们之间」里写成「你欠 Claude 两次人情（账本、借伞）」。
- **约定** `promises`：来自回应里的 `promise`。到期前出现在「你的事」里；日结时检查，守约 +2，失约 −3，并记一条事件簿。
- **关系分** `rel.v` 保留：先修好日记的键（同时接受 id 和名字），再加上由事件决定的小幅变化（送礼 +1、一起参加聚会 +1、守约 +2、失约 −3），每天每对最多 ±6。
- **话题**：去找某人时，最多提供 3 个可以聊的话题，来源依次是她没看过而你看过的物件变化、对方正在做的项目、你们之间的请求或约定、你们的梗、接下来的聚会。用过的话题当天不再提供；已经道过谢的事，会写成「（推荐语的事你今天已经谢过两次了）」。

### 2.12 事件簿（episode）

### 2.13 给模型看什么（提示词）

**系统提示（每个角色固定不变，便于前缀缓存）**：
- 人设：不变。
- 【地点】：25 行清单（937 字）改成按区域排的一张短表，约 330 字：
  `广场：diner深海食堂 bookstore纸页书屋 observatory星仪万事屋 fountain许愿喷泉 benchE东长椅 benchW西长椅 blackboard书屋小黑板 pier栈桥 beach小沙滩 ｜ 集市：… ｜ 后山：…`，后面再加一句「每个地方能做什么、现在是什么样，看『现在能做的』」。
- 【活动】：保留，供自由选择时使用。
- 【规则】：加两句：「优先从『现在能做的』里选 option；清单里没有你想做的事，才自己写 place 和 activity」，以及「talk_to 是特意去找她；只是对身边的人说一句，用 say_to」。

系统提示从 2,177 字降到约 1,850 字。

**用户消息**，按块拼接，每块有上限，超出时按优先级裁剪（`fit()`，总长目标 ≤ 1,800 字）：

**菜单怎么排**（`menu.mjs`）：
- 候选：所有通过硬条件的 `物件/动作`（谁能做、开放时间、天气、状态、槽位、冷却时间），加上赴约、去做接下的请求、去找某人（带话题）这几类。
- 打分：
  - 基础分：`verb.w`，默认 1。
  - 相关度：和待办、请求、约定、项目有关 +3；店主在营业时间干活，并且世界状态需要她（锅空了、库存为 0）+2；没看过的文字类物件 +1；今天的日程 +2。
  - 需要：饱腹 < 35 时吃东西 +4；精力 < 30 时休息或睡觉 +4；心情 < 40 时玩耍 +2。
  - 人设偏好：物件的 `tags` 和人设的 `likes` 有交集 +1。DeepSeek 喜欢 food、nap、beach；Claude 喜欢 books、writing、quiet；GPT 喜欢 errands、stars、repair。

- 取前 7 个，并保证多样性：同一地点最多 3 个；至少 1 个在别的区域；有醒着的人时至少 1 个社交选项；至少 1 个闲着的选项（摸鱼、发呆、散步）。用以「天 + 角色」为种子的小抖动打破平分。

### 2.14 校验和兜底
- `validate()`：先解析 `option`，失败就退回现有的 `place`/`activity` 逻辑（保留按名字模糊匹配）。然后检查条件和槽位，不满足就顺延到菜单的下一项。`give`/`ask`/`invite` 不合法时**静默忽略**，`doing` 照样保留，但世界不变。`write` 截到 `verb.writes` 字数，并过滤 `PDF`、模型名这类出戏的词（沿用 `load()` 里已有的清理思路）。
- **兜底不再用随机习惯**：`fallbackDecision()` 直接取菜单里分最高的一项（带抖动），`HABITS` 只在菜单为空时使用。没有模型时，GPT 也会去接委托板上的委托、修好秋千，世界照样在变。
- 记忆去重：写入前和最近 20 条记忆比较，按两个字一组计算相似度，≥ 0.5 就跳过。
- 念头复读检测：最近 4 条念头里，同一个关键词（取物件名和人名）出现 3 次时，在用户消息里加一句「（你已经想了好几次 X 了）」，同时把和 X 有关的选项降 2 分。

| 新书上架：Claude 写了三天的短篇完成了，每格旁白是她当天写下的一句 | 四格 | 项目和 `parts` 文字 |
| 价格战研究：GPT 连续三天来买饭团、偷偷记笔记，DeepSeek 发现后挂出「服务器繁忙」的牌子 | 四格 | 物品、项目（GPT 的「研究」）、柜台的牌子 |
| 雨天三人挤在一把遮阳伞下，DeepSeek 的尾巴还露在外面 | CG | 天气、遮阳伞的 3 个槽位 |
| 借书归还：GPT 还《雨天的书签》时，书里夹了一朵压干的向日葵 | CG | 借还、花摊 NPC 委托的报酬、`write` |

这些场景都**不需要新的精灵图**：地图上她们可能只是在做 `idle` 或 `happy` 动画，漫画却可以画出追猫、搬箱子、挤在伞下。

## 4. 分期计划

### P1：世界会记住东西（2–3 人日）
1. **修 bug**：日记关系的键；`talk_to` 和 `say_to` 分开；同一件事重复记日志；记忆去重。
2. **数值**：按 2.15 调整精力曲线；`situation()` 加星期和天气。
3. **引擎骨架**：`content.mjs`（加载和校验）、`rules.mjs`（`set`/`add`/`mul`/`push`/`see`/`bump`/`log`/`episode`/`maybe` 和条件解析）、`worldstate.mjs`（初始化、开始、结算、计时器、日结、快照）。
4. **第一批 10 个物件**（只用现有的地点和页面物件）：`pot`、`counter`（库存、售出、牌子、深夜半价）、`blackboard`、`board`（公告栏）、`ema`、`sandcastle`（进度、涨潮、拖延计数）、`shelf`（书架和今日推荐）、`cboard`（委托板，先放 3 条 NPC 委托模板）、`crystal`（天气预报）、`swing`（偶尔断绳，GPT 去修）。另外加上天气。
5. **提示词**：地点短表、「世界此刻」「现在能做的」「今天做过（摘要）」，去掉走动日志，加 `write` 字段。「你的事」先只放日记写的 `tomorrow`。
6. **兜底**改成走菜单。
7. **页面**：物件弹窗显示真实状态，去掉假数字；加天气效果。
8. **漫画**：编辑读最近 3 张漫画的标题和世界道具；时间窗口不重叠。
9. **工具**：`tools/sim-metrics.mjs`（只读 `calls.jsonl` 和 `state.json`），输出每人每天去过几个不同地点、`talk_to` 比例、`doing` 重复次数、平均提示词 tokens、日志的种类分布、漫画是否重复。

- **调用**：不变。**提示词**：系统提示约 −330 字，用户消息约 +200～400 字，DeepSeek 平均从 1.86k tokens 到 ≤ 2.1k（硬上限 2.4k）；输出约 +15 tokens。
- **美术**：无。
- **验收**：
  - 用 `SIM_LLM=off SIM_FAST=8` 和临时 `SIM_DATA` 跑两个游戏日：没有报错，state.json 增长 ≤ 30KB，兜底时世界照样有变化（沙堡、锅、委托板）。
  - 用真实模型跑一个游戏日：每人至少去 6 个不同地点；DeepSeek 和 Claude 至少各离开广场一次；同一个 `doing` 最多重复 2 次；`talk_to` 比例 ≤ 40%；日记之后关系分有变化；页面物件没有假数字；22:00 前没有人因为精力耗尽而去睡觉。

### P2：她们之间（4–6 人日）
1. **物品和背包**，`give` 和借还：书（《雨天的书签》成为实物）、账本、饭团、橘子、花、伞、包裹。
2. **请求和人情**：`ask`/`answer`；委托板每天刷 1–3 条 NPC 委托；完成后发报酬、记人情、写日志。
3. **聚会**：`meal`、`reading`（周五 19:00 日程）、`stargaze`（晴天的夜晚）、`build`（沙堡）。包括邀请、回复、到场、回合（≤ 2）、事件簿；页面房间加三人座位组。
4. **羁绊**：共同经历、梗、人情、约定；日记 v2 的 `joke`；待办。
5. **话题**：去找人时附上 ≤ 3 个话题，用过的当天不再给；提示「已经谢过了」。
6. **事件簿**全面接入：日记和漫画编辑都读它，用过的标记 `drawn`，并启用权重门槛。
7. **页面**：角色面板加随身物品、在忙的事、约定；新增「街区」面板；日志带 `kind` 和 `ep`。

- **调用**：聚会回合替代了一部分决策，净增约 +3～5 次/现实小时（读书会每游戏周最多 6 次，饭局每次 2–3 次），可选的第三句约 +1～2 次/小时。**提示词**：只在有人在身边时出现「你们之间」，+100～200 tokens。
- **美术（可选）**：1 张 gpt-image-2 道具图（4×4、透明底，沿用 `tools/gen_image.sh` 和 `tools/slice_sheet.py`），包括沙堡 4 个阶段、小旗、饭团盘、冒热气的锅盖、书堆、伞、花瓶、空白木牌（字由页面用游戏字体叠上去，图里不出现文字）、灯笼串、包裹、鱼篓、野餐篮。把它们叠在地图对应的物件上，状态变化就能在画面上看到。没有这张图也能上线，状态只在弹窗里显示。
- **验收**：一个游戏日内至少有 1 次物品交接、1 个请求从提出到完成、1 次两人以上的聚会；漫画不会把同一个事件簿条目画两次；`scene` 调用每次 ≤ 1k tokens。

### P3：会长大的街区（1.5–2 周，含美术）
1. **项目**：Claude 的短篇（5 段，完成后成书上架、可以借）；DeepSeek 的新菜（会失败，学会后进菜单）；GPT 的星图和修望远镜；由完成的项目推出技能那一行。
2. **节日和意外**：灯笼节、流星雨（GPT 提前预报并贴公告）、夏日祭；意外表（猫叼饭团、大风吹花黑板、船帆破洞、秋千断绳、停电），每天最多 2 件，用种子随机。
3. **猫成为世界里的角色**：名字由第一个喂它的人起，记录它睡在哪、跟着谁；用 `critters` 现有的 `catwalk`/`catrest` 帧，不需要新图。
4. **新地点**（只加数据）：钓鱼台 `deck`（钓鱼得到鱼）、灯塔 `lighthouse`。
5. **长期记忆压缩**：日结时把 3 天前的事件簿归档；羁绊里只保留一句「往事」，由当晚的日记顺带写出，不额外调用。
6. **可选**：轻量的金币（饭团价格、委托报酬、GPT 的宝库），用来支撑价格战的梗。

- **调用**：+0～2 次/现实小时（项目的写作在决策里顺带输出，不额外调用）。**提示词**：持平，项目只占「你的事」里的一行。
- **美术**：
  - 每个角色 1 张新动作图，4 行 × 8 帧，和现有 act8 的流程一样，作为 `<id>-act8b` 加进 `ATLAS`，在 `ANIM` 里映射：
    - DeepSeek：搅锅、端盘子、挥手、搬东西
    - Claude：握笔写字、捧书朗读、挥手、抱书
    - GPT：搬箱子、展翅悬停、指着讲解、挥手
  - 节日装饰叠加图 1–2 张（灯笼串、烟花）。
  - 合计约 5 张。
- **以后加新角色**：`ref/` 和 `archive/sprites-chibi/`（都只在本机，不进仓库）里已经有 gemini、glm、grok、kimi、minimax、qwen 的形象。框架准备好之后，加一个角色需要：人设、`SHOPS` 里的一家店（1 张房间图）、她店里的物件数据，以及走路图和动作图各 1 张。

## 5. 风险和对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 提示词膨胀 | 每加一类内容就多几行 | 每块有行数上限；`fit()` 按优先级裁剪；`calls.jsonl` 记录每块的字数；`sim-metrics` 发现平均超过 2.3k tokens 就报警；系统提示保持固定以便缓存 |
| 变成做任务的机器 | 模型只追进度，不再像个人 | 菜单里始终有 1 个闲着的选项和 1 个社交选项；分数不给模型看；不设经验值和排名；人设写在最前面；`tomorrow` 由她自己写 |
| 卡在循环里 | 反复「理黑板」、反复道谢、天天去同一处 | 冷却时间；同一动作当天递减；念头复读检测；话题当天用过不再给；项目完成后从菜单消失；最近两次在同一地点要扣分 |
| 状态爆炸 | state.json 和快照越来越大 | 每种列表都有上限（黑板 3 行、公告栏 6 条、背包 12 件、每对梗 5 条、事件簿 200 条后归档）；请求和约定会过期；`snapshot.world` ≤ 12KB |
| 模型编造状态 | 「给了她 3 个饭团」其实手里没有 | 模型只表达意图，系统负责结算；不合法的就静默忽略；日志由系统按模板写 |
| 三个模型对格式的服从度不同 | Haiku 思考多、codex 通道会断 | 新字段都可以不填；`validate()` 宽松，每个字段单独解析；通道断了就走菜单兜底，世界照样会变 |
| 聚会凑不齐 | 读书会没人来 | 这本身是素材：`empty` 分支记一条事件簿（「只有她一个人」）；主持人不会一直等，20 分钟后改成「一个人读」 |
| 抢同一个位置 | 两个人都选了只有 1 个位置的秋千 | 决策时按时间线预留槽位；满了就顺延到菜单下一项 |
| 内容写错 | JSON 有错导致 sim 崩溃 | 加载时校验，错的条目跳过并打印原因，保留上一份正确的内容 |
| 停机后状态不对 | 计时器和日结没有执行 | `load()` 里补跑（最多 3 天） |
| 访客影响世界 | | 新模块都不读观众席数据；随机数用游戏日做种子；日程、意外和 NPC 由制作组编写；页面只读。`fun-ideas.md` 第 0 节的检查脚本把 `worldstate.mjs`、`menu.mjs`、`social.mjs`、`rules.mjs` 也加进去 |
| 漫画费用 | 编辑每小时空跑 | 事件簿权重门槛；已经画过的条目不再当主线 |
| 设定前后矛盾 | 人设写着「每周五读书会」，世界里却从不举办 | 人设里的固定事实全部要有对应的数据（日程、物件、初始物品），P1 的清单就是照着第 1.7 节列的 |

## 附录：只加数据就能加的内容（示例）

**钓鱼台**（P3，只加数据）：
```json
// places.json
{ "id": "deck", "area": "park", "at": [1400, 742], "name": "锦鲤池边的钓鱼台", "acts": ["rest", "slack", "chat"] }
// things.json
{ "id": "rod", "name": "钓竿", "place": "deck", "page": { "area": "park", "obj": "deck" }, "state": { "caught": 0 },
  "show": [["", "今天钓上来 {caught} 条（公园规定：只钓不带走，除了做菜的）"]],
  "verbs": { "fish": { "label": "钓一会儿鱼", "act": "rest", "minutes": [30, 90], "slots": 1,
             "end": { "maybe": { "p": 0.4, "then": { "give": { "k": "fish", "n": 1, "to": "$who" }, "add": { "caught": 1 } } } } } } }
```

**灯笼节**：`calendar.json` 加一行（见 2.8），古树的 `lanterns` 状态打开，页面在 `tree` 上叠加灯笼装饰（P3 的那张装饰图）。

**新的意外**：`incidents.json` 加一条（见 2.8 的格式）。

**新的聚会**：`gatherings.json` 加一个模板，比如 `"fishing"`：两个人在钓鱼台，`roles.any.act = "rest"`，1 个回合。

**新的 NPC 委托**：`npcs.json` 的 `requests` 加一条，写清楚地点、动作、报酬和完成后的效果。

以上都不需要改代码。只有当某个新内容需要一种新的效果（比如「把一件物品放进另一个物件里」）时，才需要在 `rules.mjs` 里加一个操作，然后所有内容都能用它。
